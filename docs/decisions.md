# BeONE 결정 기록

구현 전 미결 사항과 확정 결정을 기록합니다. 요구사항의 기준은 [PRD](PRD.md)입니다.

- 결론이 정해지기 전에는 `상태: 미결`로 두고, 담당자·기한·결론을 추측해 채우지 않습니다.
- 결정되면 결론, 근거(약관·자료 출처), 결정일을 적고 상태를 `확정`으로 바꿉니다.
- 미결 사항을 검증된 사실이나 이미 구현한 기능으로 표시하지 않습니다(PRD §11).

D-01은 사용자에게서 실제 카드 표시명과 카드 뒷면 후불교통 표기를 확인했으나 **공식 SKU·약관 버전의 일치 여부는 미결**이다. 카드 유효기간은 공개 문서에 기록하지 않으며 발급일·약관 적용일로 추정하지 않는다. D-03·D-04는 아래 **구현 정책만 확정**했으며, 개별 거래의 적용 규칙 버전·실계정 필드 가용성·미확정 약관 조건이 검증됐다는 뜻이 아니다. D-08은 실기기 PoC 결과로 시연 기기·인증 정책·앱 복귀 정책만 확정했으며, BeONE 앱에 인증 기능이 구현됐다는 뜻이 아니다. D-06은 사용자의 직접 검증 및 통과 확인을 반영했으며 D-07 등 다른 미결 항목은 그대로 둔다(D-09는 2026-11-01 확정).

D-10~D-12는 PRD §11의 미결 목록이 아니라 평가 사례 20개·입력 변경 시험 10개 초안을 검토하며 해석이 갈린 규칙을 정한 결정이다. 이 결정이 평가 자료를 검증 완료로 만들지는 않으며, D-06은 사용자의 직접 검증 및 통과 확인을 반영했으며, 자세한 검토 증빙은 노션의 「D-06 사람 교차 검토」 문서를 참조한다.

D-13도 PRD §11의 미결 목록이 아니라 단일 주문 혜택 계산의 결과 타입을 설계하며 정한 방향이다. 결과 타입의 큰 구조만 정했으며, 상세 타입·금융 정책·구현을 승인하거나 공식 약관 검증을 뜻하지 않는다.

D-09는 PRD §11-9의 결정이며 MVP 한정 임시 방식이다. D-14는 PRD §11의 미결 목록이 아니라 업무 API 명세를 쓰기 전에 범위와 공통 원칙을 정한 결정이다. 두 결정 모두 API·DB·인증 구현을 뜻하지 않는다(2026-11-01 기준 업무 API·테이블·인증 계층 없음).

D-15~D-17은 PRD §11의 미결 목록이 아니라 업무 API 명세 전에 정한 데이터 처리 정책이다. 근거는 사용자 결정이며, 공식 SKU·약관 버전 확인(D-01), 규칙의 `VERIFIED` 승인, 실계정 응답 검증을 뜻하지 않는다. 2026-11-02 기준 이 정책을 구현한 코드는 없다.

### D-03·D-04 확정 정책

**D-03 기간·계산 범위.** 시연용 4종의 거래 기반 월간 금전 혜택(적립·청구/환급 할인)을 대상으로 한다. 공항라운지·발레파킹과 은행 수수료 면제는 월간 결제 혜택 최적화에서 분리한다. 각 규칙에는 전월 실적 기간, 혜택 적용 기간, 거래 기준일(승인/이용/명세서 기재/매입), 한도 차감 순서, 신규 사용등록 유예, 출처와 적용 가능한 규칙 버전을 별도 표현한다. 동일한 달이라는 이유로 서로 다른 기준일을 합치지 않는다.

기준유가, 선택 서비스 이력, 톡톡 취소 귀속월, 교통 기재일, 지연된 한도 복원, 중복 적용·원 미만 금액 처리, 과거 규칙의 실제 적용 시작일 등 **필수 근거가 없는 혜택은 `확인 필요`로 표시하고 확정 계산에서 제외**한다(D-05). 계산 가능한 부분은 출처와 누락 범위를 붙여 조건부로만 표시한다. 미확인 혜택 때문에 순위가 바뀔 수 있거나 비교 가능한 카드가 부족하면 “월간 최적 카드”라고 단정하지 않는다(PRD FR-05). PDF 파일명 날짜를 혜택 버전의 효력 시작일로 쓰지 않는다. 이 표는 목표 모델 범위이지 구현 완료나 모든 혜택의 `VERIFIED` 선언이 아니다.

**D-04 상태 출처.** 아래 분류는 필드가 실제 KB 응답에 존재하고 의미·기간이 맞는지를 확인한 뒤 적용한다. 원시 실계정 응답 전문을 저장하지 않는다.

| 분류 | 계산 입력으로 다룰 수 있는 범위 | 확인 경계 |
| --- | --- | --- |
| `CODEF` 직접 조회 사실 | 반환된 카드 표시명·종류·상태·발급일·교통 여부, 승인 일시·금액·취소 신호, 실적조회 금액·충족 여부·조회 기간의 **제공된 값만** 정규화 | 상품 SKU·약관 버전, 카드사 인정 실적의 전체 의미, 월 혜택 잔여한도, 공식 업종·결제수단을 자동 확정하지 않는다. |
| `INFERRED` 규칙 기반 산출 | 적용일이 검증된 `VERIFIED` 규칙과 누락 없이 순서가 확인된 거래 원장에서 전월 인정 실적·당월 혜택 사용액/잔여한도를 재계산 | 원장 불완전·취소 접수일/매입순서 누락·타 카드 합산 실적 불명 시 해당 값을 `UNKNOWN`으로 둔다. 후보 업종·가맹점 이름만으로 확정하지 않는다. |
| `MANUAL` 사용자 확인 | 선택 서비스·변경 이력, 등록일/유예, 자동납부·간편결제·가맹점 분류, 조회와 충돌하는 실적·한도 등 필수 상태를 기간과 함께 입력 | 사용자의 값은 출처가 `MANUAL`이며 공식 SKU·약관 버전의 독립적인 증거가 아니다. CODEF와 다르면 계산 기준을 명시적으로 선택받는다. |
| `SYNTHETIC` / `UNKNOWN` | 가상 보유·거래는 실제 조회와 분리하고, 미제공·불일치·기간 불명·오래된 값은 미확인으로 유지 | `UNKNOWN`을 0원으로 바꾸지 않는다. 가상 상태를 실제 보유카드나 실계정 관찰로 표시하지 않는다. |

각 상태값에 **출처, 기준 기간, 갱신시각, 적용 규칙 버전(산출값인 경우)**을 붙인다(PRD FR-02·FR-03). 전체 카드번호가 반환되면 앱 모델·저장·로그·브라우저 전달 전에 제거한다. 카드별 조회에 전체 번호가 필수라면 카드번호 비수집 원칙과 충돌하므로 구현 전 별도 보안 결정을 요구한다. 실제 두 카드의 상품 매핑(D-01)은 `CANDIDATE`로 남기며, 표시명·RF·교통 표기만으로 `USER_CONFIRMED` SKU라고 하지 않는다.

### D-08 확정 정책

**시연 기기.** Samsung SM-S942N(Android 16, One UI 8.5, 보안 패치 2026-08-05)을 사용한다. 지문을 등록하고 화면 잠금을 PIN으로 설정한다. 이 기기에서 지문은 `BIOMETRIC_STRONG`, 얼굴은 `BIOMETRIC_WEAK`로 보고되므로 얼굴인식은 시연 인증 수단으로 사용하지 않는다.

**인증 정책.** `BiometricPrompt`에 `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`을 지정한 단일 프롬프트를 사용한다. 지문을 사용할 수 없거나 잠기면 같은 프롬프트에서 기기 PIN으로 진행한다(PRD §4.3-2). 얼굴(`BIOMETRIC_WEAK`) 허용 방식은 실기기에서 수동 전환과 확인 버튼이 필요했고, 별도 PIN 프롬프트 방식은 단계와 구현이 늘어나 채택하지 않았다.

**앱 복귀.** 활성 중 앱이 백그라운드로 가면 즉시 비활성화하고, 복귀하면 재인증을 안내한다. 회전·폴드·테마 변경처럼 화면 구성만 바뀌는 경우는 앱 이탈로 보지 않는다.

| 확인 범위 | 상태 |
| --- | --- |
| 지문 성공 → 60초 활성화, 만료·취소 시 비활성화와 재인증 안내, 재인증 | 실기기 확인 |
| 지문 불일치 반복 → 잠김 → 같은 프롬프트에서 PIN 대체 | 실기기 확인 |
| 앱 이탈 시 즉시 비활성화, 복귀 시 재인증 안내 | 실기기 확인 |
| WebView에 성공·취소·불일치 상태 전달과 복귀 시 상태 동기화 | 실기기 확인 |
| 생체 미등록 상태에서 PIN으로 진행(PRD §4.3-2) | **남은 검증**: 본 앱 구현 후 FR-06 실기기 검증 |
| 화면 잠금 미설정 시 설정 안내, 활성화하지 않음(PRD §4.3-5) | **남은 검증**: 에뮬레이터 결과만 있음 |

이 인증은 앱 내 가상 결제 화면의 활성화 트리거이며, 실제 카드 소유 증명·카드사 결제 인증·서버가 신뢰하는 승인으로 사용하지 않는다(PRD §4.3, FR-06). 결과 확인은 PoC 앱으로 했으며, BeONE 앱 구현의 최종 확인은 FR-06 완료 조건에 따라 같은 실기기에서 다시 한다.

### D-10~D-12 확정 정책

2026-10-08 사용자가 평가 사례 초안(PR #10)의 AI 재계산·반박 검토 중 해석이 갈린 세 가지를 정했다. 아래 내용은 해당 카드의 공식 자료와 [카드 규칙 조사](card-benefit-research.md)를 근거로 한다. 실제 보유 카드의 SKU·약관 버전(D-01)과는 무관하다.

**D-10 노리 체크카드(`01664`) 통신요금 할인.** 공식 상품설명서 1쪽의 통신요금 할인 항목에는 "이동통신요금 자동납부 시 5% 환급할인"과 "건당 이용금액 5만원 이상 시 2천 5백원 정액할인(월 1회)"이 함께 적혀 있다. 50,000원의 5%가 2,500원이고 "정액"·"월 1회"가 명시되어 있으므로 두 줄을 한 혜택으로 읽는다.

- 계산: 건당 이용금액 5만원 이상이면 **2,500원 정액**, 월 1회. 5만원 미만이면 0원이다. 5% 요율로 계산하지 않는다.
- 조건: 해당 카드로 자동이체 등록, 전월 이용실적 30만원 이상, SKT·KT·LG U+ 한정, 유무선 통합청구금액 자동이체는 제외.
- **"건당"은 한 번의 출금 금액이다.** 한 달 동안 여러 번 나눠 출금된 금액을 더하지 않는다. 예를 들어 30,000원과 20,000원이 따로 출금되면 각각 5만원 미만이므로 할인은 0원이다. 통신요금은 보통 한 달에 한 번 출금되므로, 실제로는 월 청구액이 5만원 이상인지를 보는 것과 비슷하다. 합산하지 않는다는 것은 "건당"이라는 표현에 따른 해석이다.
- **"자동이체 등록"은 금액과 별개의 조건이며 사용자가 확인하는 값이다.** 금액 조건은 한 번에 얼마가 출금됐는지, 자동이체 등록은 이 카드로 통신요금이 자동 출금되도록 설정해 두었는지를 뜻하고 둘 다 충족해야 한다. 카드로 직접 결제한 50,000원은 금액이 맞아도 자동이체가 아니므로 0원이다. 카드 승인내역만으로는 직접 결제와 자동이체를 확정하기 어려우므로(D-04의 `MANUAL`) 실제 카드 모드에서는 사용자가 카드 설정에서 한 번 입력하고 출처·기준 기간과 함께 저장한다. 답하지 않으면 `확인 필요`로 두고 통신 할인을 확정 계산에서 제외한다(D-05). 평가 자료의 `paymentMethod: AUTOPAY`는 이 조건을 입력값으로 단순화한 것이다.
- 한계: 약관이 "5만원을 넘어도 2,500원"이라고 직접 쓰지는 않는다. 읽는 방식에 대한 결정이며 약관 원문이 이를 명시한다는 뜻이 아니다. "월 1회"가 한 달 중 어떤 결제에 적용되는지(조건을 처음 충족한 건인지 등)는 구현 전 확인한다.

**D-11 올라운드 티타늄(`09271`) 포인트리 적립.** 공식 상품설명서 1쪽은 국내외 전 가맹점 1% 포인트리 적립(전월 실적조건·적립한도 없음)과 "KB국민카드의 포인트리 1점은 1원과 가치가 동일"함을 적고 있다. 적립은 해당 이용분의 결제일 다음 영업일에 이뤄지고 취소 시 차감된다.

- 계산: 1% 적립을 **1점=1원인 혜택**으로 포함한다. D-03의 대상 범위(적립·청구/환급 할인)와 같다.
- 표시: "적립(포인트리)"과 "청구·환급 할인"을 구분하고, 카드사가 실제 지급한 금액이 아닌 예상 혜택으로 표시한다.
- 적립 지급일은 혜택 산정 기준일과 구분한다(D-03). 원 미만 금액 처리는 D-03의 미확정 상태를 유지한다.

**D-12 혜택이 같을 때의 카드 선택 규칙.** 비교는 확정된 원 단위 금액으로만 하며, 아래 순서로 첫 번째로 가려지는 단계에서 정한다.

1. 월간 총예상 혜택이 큰 카드
2. 현재 주문 혜택이 큰 카드
3. 동률 카드 중 사용자가 지정한 대표 카드가 있으면 그 카드
4. 카드 ID 문자열 오름차순(내부 상품 식별자, 예: `01914`이 `09271`보다 앞). 숫자로 변환해 비교하지 않는다.

3·4단계는 혜택 금액으로 가릴 수 없을 때 결과를 항상 같게 하려는 **임의 규칙**이다. 선택된 카드가 더 좋다는 뜻이 아니며, 소득공제·후불 여부·계좌 잔액 같은 엔진이 계산하지 않는 요소는 반영하지 않는다. 체크·신용 구분은 우선순위에 넣지 않는다. 선호가 있으면 대표 카드 지정, 대표 카드 고정, 추천 제외 카드로 조정한다.

- 표시: 동률 카드 목록, 사용한 기준(대표 카드 또는 카드 ID 순), 차선 카드 대비 차액 0원을 보여 주고 임의 규칙으로 정해졌음을 표시한다.
- 필수 상태가 `확인 필요`인 카드의 금액은 확정되지 않았으므로 동률 여부는 확정된 금액끼리만 비교한다. 그 미확인 값이 어떤 값이어도 동률 규칙(대표 카드, 카드 ID 순)까지 적용한 최종 선택 카드가 달라지지 않는다고 확인될 때만 확정 최적 추천을 한다. 선택 카드가 달라질 수 있거나 비교 가능한 카드가 부족하면 확정 최적 추천을 하지 않는다(D-03, D-05, PRD FR-05).
- 카드 ID는 KB 상품 페이지의 식별자이며 CODEF 응답 코드가 아니다. 실제 카드 모드의 카드 ID와 자동 추천 모드에서 동률용 대표 카드를 지정하는 설정 방식은 구현 전에 별도로 정한다.
- PRD FR-05의 동률 문장을 이 순서에 맞게 수정한다.

### D-13 확정 정책

2026-10-28 사용자가 단일 주문 혜택 계산의 결과 타입 설계를 검토하며 확인한 설계 방향을 기록한다. 근거는 사용자 확인이며, 외부 약관 근거가 있는 결정이 아니다. 2026-10-28 기준 코드에는 `OrderBenefit` 타입이 없으며 구현되지 않았다. `OrderBenefit`은 #35에서 아래 2026-10-31 결정에 따라 추가했다.

**확정한 것**

- 단일 주문 결과는 신규 `OrderBenefit` 타입으로 분리한다.
- 기존 결과 타입의 현재 계약은 유지한다.
  - `CardBenefit`은 현재 주문의 혜택 `currentOrderBenefit`, 현재 주문의 서비스별 결과 `services`, 현재 주문을 그 카드로 결제할 때의 월간 총예상 혜택 `monthlyTotal`을 함께 담는다.
  - `Recommendation`은 추천 입력 하나에 대한 카드별 결과와 선택 결과를 담는다.
  - `ApplicationStatus`·`ServiceBenefit`의 의미와 계약도 그대로 둔다.
- `OrderBenefit`을 도입한다는 이유로 기존 필드를 삭제하거나 대체하지 않는다.
- 같은 주문의 혜택을 중복 계산하거나 합산하지 않는다. D-12가 비교에 쓰는 `monthlyTotal`·`currentOrderBenefit`을 제거하거나 다르게 해석하지 않는다.
- 서비스의 조건 판정(조건을 충족했는지)과 최종 채택 여부(그 카드의 최종 금액에 넣었는지)를 분리한다. 채택 여부는 `ADOPTED`(채택), `NOT_ADOPTED`(채택하지 않음), `UNDETERMINED`(채택 여부를 정할 수 없음) 세 가지이다.
- 최종 카드 금액에 실제로 들어가는 서비스별 기여액 `contribution`을, 채택 여부를 정하기 전에 서비스별로 계산한 후보 금액과 구분한다.

### D-09·D-14 확정 정책

2026-11-01 사용자 결정. 근거는 사용자 결정과 PRD §2·§3·§4·§7, FR-03·FR-06·FR-07, D-04·D-05·D-08·D-12이다. 외부 약관 근거가 있는 결정이 아니다.

**D-09 사용자 식별(MVP 한정 임시 방식)**

- 사용자 구분: 시드로 넣은 고정 사용자 2명(내 카드 사용자, 가상 포트폴리오 사용자)을 쓴다. 가입·로그인·BeONE 계정 비밀번호는 MVP에 넣지 않는다.
- 현재 사용자 결정 지점: "지금 요청한 사용자"는 한 곳(예: `CurrentUserResolver`)에서만 정한다. 컨트롤러·서비스는 그 결과만 받아 쓰고 요청 값에서 사용자 ID를 직접 읽지 않는다. MVP 구현은 고정 사용자를 돌려준다.
- 엔드포인트: 사용자 ID를 URL 경로나 요청 본문에 넣지 않는다. `/users/{id}/...`는 쓰지 않고 `/me/...` 형태를 쓴다. 로그인을 붙여도 API 명세가 바뀌지 않게 한다.
- 데이터: 카드·원장·CODEF 연결(`connectedId`) 등 사용자 데이터는 처음부터 `user_id`로 나눠 저장한다. 나중에 로그인 사용자와 그대로 연결할 수 있어야 한다.
- 사용자 전환: 시연에서 두 사용자를 바꾸는 방법(서버 설정값, 시연 전용 헤더 등)은 API 명세에서 정한다. 이 방법은 로컬·시연 환경에서만 켜지게 한다.
- 노출 범위: 서버는 로컬·시연 환경에서만 띄우고 외부에 공개하지 않는다. 내 카드 모드에는 실제 CODEF 데이터가 들어가므로, 공개 배포가 필요해지면 시연 접근 키나 로그인을 먼저 붙인다.
- 응답·오류: 공통 응답·오류 구조에 인증 필요(401)·권한 없음(403) 오류 코드 자리를 예약한다. MVP에서는 쓰지 않는다. 공개 `code` 값은 업무 API 명세에서 정한다.
- 기기 인증과의 관계: Android 기기 인증은 화면 활성화 트리거이며(D-08) 서버가 사용자를 식별하거나 권한을 주는 근거가 아니다.
- 세션 로그인으로 바꿀 때 고칠 지점: ① 현재 사용자 결정 지점(`CurrentUserResolver` 등)의 구현, ② 시연용 사용자 전환 방식 제거·대체, ③ 노출 범위(공개 배포와 HTTPS 전제). API 경로·본문과 `user_id` 기준 데이터 구조는 그대로 둔다.
- 채택하지 않은 안: MVP 세션 로그인(가입·비밀번호 저장·WebView 쿠키 처리로 일정 위험), 기기 단위 식별(기기 식별자를 다루고 서버가 검증할 수 없는 값을 신뢰), 토큰 인증(발급 주체가 필요해 범위 증가).

**D-14 업무 API 범위와 명세 순서**

- 단계: 1차는 수동 입력·가상 포트폴리오 경로, 2차는 CODEF 연결·조회·매핑 확인이다. CODEF는 필수 범위이며 2차는 선택 사항이 아니다. CODEF 전송 계약 결정 직후 바로 명세하고, 1차가 끝날 때까지 미루지 않는다.
- 1차 명세 순서(시연 흐름 기준): 카드 상품 조회 → 보유 카드·월간 상태(수동) → 결제 전 설정 → 주문·예정 소비 → 추천 → 모의 승인·취소 → 가상 원장 조회. 일정이 밀리면 뒤쪽 조회 기능부터 줄이고 설정 → 주문 → 추천 → 모의 승인·취소 흐름은 지킨다.
- 2차를 받을 수 있는 1차 모델: 보유 카드와 월간 상태에 출처(`MANUAL`·`CODEF` 등)와 확인 상태(확인됨·확인 필요·매핑 실패 등)를 처음부터 둔다. 2차에서는 CODEF로 이 데이터를 채우는 API만 더하고 1차 API 형식은 바꾸지 않는다. 확인 상태의 정확한 값 목록은 명세 단계에서 D-04에 맞춰 정한다.
- 미확인 값: 알 수 없는 실적·조건·혜택은 응답에서 `확인 필요`로 드러내고 0원이나 해당 없음으로 바꾸지 않는다. 확정 추천 계산에서는 빼고 그 이유를 응답에 담는다(D-05).
- 사용자 기준: 모든 업무 API는 D-09에 따라 `/me` 형태의 현재 사용자 기준이다.
- AI 보조(FR-08): 업무 API에 넣지 않는다(API 밖 도구). 필요하면 따로 정한다.

**D-14 업무 API 공통 원칙**

1. 경로: 모든 업무 API는 `/api/v1` 아래에 두고, 사용자 기준 자원은 `/api/v1/me/...` 형태로 쓴다.
2. 응답·오류: [공통 응답·오류 형식](api.md)을 따른다(성공 `{data}`, 실패 `{code, message, errors}`, `errors`는 항상 배열, `204`는 본문 없음). 계산 상태(확인 필요·범위 밖 등)는 오류가 아니라 `data` 안에 담는다.
3. 금액: 원 단위 정수이고 필드 이름은 `...Won`으로 끝낸다. 모르는 값은 `null`과 상태값을 함께 주고 0으로 대신하지 않는다.
4. 출처: 출처(`MANUAL`·`CODEF`·`INFERRED` 등)·기준 기간·갱신 시각은 D-04대로 각 상태값마다 붙인다. 같은 메타데이터를 공유하는 값끼리는 데이터 묶음 단위(카드 1장의 월간 상태, 규칙 1개, 추천 결과 1건 등)로 줄여 표기할 수 있다. 2026-11-01 리뷰 대조로 D-04와 맞춰 정정했다(처음 문구는 "값 하나하나가 아니라 묶음 단위"였다).
5. 추천·승인 근거: 추천·승인 응답에는 규칙 버전, 근거 출처, 선택 이유, 동률일 때 고른 기준(D-12)을 담는다.
6. 중복 방지: 모의 승인과 모의 취소 모두 `Idempotency-Key` 헤더를 받는다. 보존 기간과 같은 키·다른 본문일 때의 응답은 명세 단계에서 정한다.
7. 승인 직전 재계산: 승인은 주문 ID로 받고 서버가 다시 계산한다. 재계산 결과가 사용자가 본 추천과 다르면 응답에 차이와 이유를 담는다(FR-07, PRD §4.4).
8. 기기 인증: 서버는 Android 기기 인증 결과를 신뢰하지 않으며(D-08), 기기 인증 여부를 근거로 서버 권한을 주지 않는다.
9. 민감 정보
   - 카드번호·실물 카드 비밀번호(앞 2자리 포함)·CVV·유효기간 필드를 두지 않는다. KB 카드소지확인은 [KB 조회 조건](domains/codef-kb.md)대로 지원 보류(수동 입력 대체)를 유지한다.
   - 요청 본문으로 받는 비밀 값은 CODEF 연결(`connectedId` 등록)에 필요한 카드사 홈페이지 로그인 아이디·비밀번호뿐이다. 인증서 로그인(인증서 비밀번호·인증서 파일)을 MVP에 넣을지는 별도 결정이 필요하며 허용하지 않은 상태다.
   - 받은 비밀번호는 저장·로그·응답·오류 메시지에 남기지 않는다. 서버는 받은 즉시 CODEF 공개키로 암호화해 전송하고 원문은 폐기한다. 로컬 시연 밖으로 공개할 때는 HTTPS를 전제로 한다.
   - 실물 카드 비밀번호를 받는 경로가 필요해지면 `CLAUDE.md`·PRD §7·KB 조회 조건 문서를 함께 바꾸는 별도 보안 결정으로 다룬다.

**한계와 후속**

- 범위와 원칙만 확정했다. 개별 API의 경로·필드·nullable 정책, 확인 상태 값 목록, 멱등 키 세부, 사용자 전환 방식, 예약 오류 코드의 공개 값은 API 명세 단계에서 정한다.
- 명세 단계에서 팀의 기존 API 명세 초안(노션, 약 39개 API)과 공통 응답·예외 처리 가이드를 대조해 이어 쓸 것과 바꿀 것을 표로 정리한다. 기존 초안을 근거 없이 버리거나 그대로 복사하지 않는다.
- 추천 응답 구조는 카드 간 비교의 미결 항목(D-13 미결: 카드 단위 사유 우선순위, 공유 한도 배분)과 취소 귀속·상품 매핑(D-01·D-04 세부) 결정에 따라 확정한다.
- 업무 API·DB 테이블·인증 계층·CODEF 호출은 2026-11-01 기준 구현되지 않았다.

### D-15·D-16·D-17 확정 정책

2026-11-01 사용자 결정. 근거는 사용자 결정과 D-01·D-03·D-04·D-05·D-12·D-13·D-14, [KB 조회 조건](domains/codef-kb.md)(Aside 수집 공식 시트, 실계정 관측 없음)이다. 외부 약관 근거가 있는 결정이 아니다.

**D-15 상품 매핑**

보유 카드(수동 등록 또는 CODEF 보유카드)를 규칙 카드 4종(`09271`·`09174`·`01664`·`01914`)과 연결하는 방식이다. 가상 포트폴리오 카드는 규칙 카드 자체(`SYNTHETIC`)이므로 이 매핑의 대상이 아니다.

- 매핑 상태
  - `UNMAPPED`·`CANDIDATE`·`USER_CONFIRMED`로 시작한다.
  - 나중에 공식 SKU·약관 버전을 확인하면 상태를 하나 더할 수 있게 둔다(예: `OFFICIALLY_VERIFIED`). 그래도 API 형식은 바뀌지 않게 한다.
- 계산 허용
  - 혜택 계산에는 `USER_CONFIRMED`만 쓴다.
  - `CANDIDATE`는 카드명이 정확히 같아도 자동으로 확정하지 않으며, 계산에서는 `확인 필요`다.
- CODEF 카드명은 후보를 보여 주는 데만 쓴다. KB 보유카드 응답에는 상품코드가 없으므로 카드명만으로 매핑을 확정하지 않는다(D-04).
- 기록: 매핑마다 확인한 방법(수동 선택 / CODEF 후보 확인), 확인 시각, 후보를 낸 근거(카드명 등)를 남긴다.
- 표시: 사용자 확인 매핑으로 계산한 결과에는 "사용자 확인 매핑, 공식 SKU·약관 버전 미검증"을 표시한다. 이 표시 때문에 규칙의 검증 상태가 올라가지 않는다.
- 매핑을 바꾸거나 취소하면 그 카드의 기존 계산 결과는 다시 계산하거나 `확인 필요`로 되돌린다.
- 매핑되지 않은 카드
  - 보유 카드 목록에는 보이고, 추천 비교에서는 제외한다. 제외 이유는 둘로 나눈다.
    - 매핑 미확인(`UNMAPPED`·`CANDIDATE`): "매핑 확인 필요"와 확인할 수 있는 후보를 담는다. 사용자가 확인하면 추천에 들어갈 수 있다.
    - 지원 규칙 없음: 사용자가 4종 중 어느 것도 아니라고 확인한 카드다. "검증된 규칙 없음(지원 범위 밖)"을 담는다. 사용자가 직접 지정할 수 있다.
  - 제외된 카드의 혜택 금액은 `null`과 상태값으로 주고 0원으로 바꾸지 않는다(D-05).
  - 추천 응답에는 비교한 카드 목록과 제외한 카드 목록을 함께 담고, 제외한 카드마다 이유를 적는다.
  - 제외된 카드는 동률 처리(D-12)의 대표 카드 후보에서도 뺀다.
  - 비교할 수 있는 카드가 하나도 없으면 추천을 "확정 불가"로 두고 이유를 담는다. 임의의 카드를 추천하지 않는다.
  - 제외된 카드의 실제 사용 내역이 다른 카드의 실적·한도에 주는 영향은 계산하지 않는다. 필요해지면 따로 정한다.
- D-01은 미결로 유지한다.

**D-16 상태값 변환과 출처 충돌**

D-04 정책과 D-14 원칙 4(출처·기준 기간·갱신 시각을 각 상태값마다 붙임)를 전제로 한다.

1차 수동 입력
- 엔진 입력 필드를 모두 수동으로 받는다: 전월 실적, 한도 버킷별 사용액, 다른 버킷 사용액, 선택 서비스, 등록일.
- 입력하지 않은 값은 `UNKNOWN`이다. 사용자가 0을 직접 입력한 경우만 0으로 본다. 응답에서도 둘을 구분한다.
- 일부만 입력해도 저장할 수 있다. 빠진 값 때문에 판정할 수 없는 서비스는 `확인 필요`로 두고, 어떤 값이 빠졌는지 이유에 담는다.
- 값마다 출처 `MANUAL`, 기준 기간, 입력 시각을 붙인다. 기준 기간이 카드의 실적·한도 기간(D-03)과 맞지 않으면 그 값을 계산에 쓰지 않고 `확인 필요`로 둔다.
- 이중 계산 방지: 수동으로 넣은 이번 달 사용액은 입력 시각 기준 스냅샷이다. 그 뒤에 생긴 모의 승인·취소만 더하거나 뺀다. 입력 시각 전 거래를 다시 더하지 않는다(D-17).
- 가상 포트폴리오 사용자의 값은 시드 데이터이므로 `MANUAL`이 아닌 별도 출처(`SYNTHETIC`)로 표시한다.
- 음수 전월 실적 입력은 받는다(D-17).
- 선택 서비스는 적용일을 함께 받는다. 적용일이 없으면 그 서비스는 `확인 필요`다.
- 화면에서 묻는 순서와 필수·선택 입력 구분은 API 명세 단계에서 정한다.

2차 CODEF 변환
- 보유카드는 `HeldCard`(보유 출처 `CODEF`)로 옮긴다. 카드명은 D-15에 따라 매핑 후보로만 쓴다.
- 승인내역은 CODEF 원장 거래로 옮긴다. 취소 행은 D-17을 따른다.
  - 원장 거래에서 전월 실적·한도 버킷 사용액을 자동으로 산출하지 않는다. 제외 항목·거래 기준일 근거가 없기 때문이다.
  - 원장 기반 산출(`INFERRED`)은 따로 정한다.
- 판단 불가 행이 있는 기간은 원장을 "불완전"으로 표시하고, 그 기간 값에 기대는 계산은 `확인 필요`로 둔다.
- 실적조회 금액
  - "카드사 조회 실적(참고)"으로 화면에 보여 주되, 전월 실적에는 자동으로 넣지 않는다(`UNKNOWN`).
  - 사용자가 참고값을 보고 직접 확인·입력한 전월 실적은 출처 `MANUAL`로 저장하고, 참고한 CODEF 조회값(조회월, 조회 시각)을 함께 남긴다.
  - 참고값을 미리 채워 보여 줄 수 있지만, 사용자가 확인하기 전에는 계산에 쓰지 않는다.
- 재결정 조건: 실계정에서 실적조회 금액과 카드사 명세서·앱의 인정 실적이 일치하는지 확인되면, 기간이 일치하는 카드의 자동 반영을 다시 검토한다. 그 전까지는 자동 반영하지 않는다.

출처 충돌
- 충돌로 보는 경우: 같은 카드·같은 항목·같은 기준 기간에 출처가 다른 값이 둘 이상 있고 값이 서로 다를 때만이다.
- 충돌로 보지 않는 경우
  - 값이 같은 경우. 출처는 모두 기록한다.
  - 기준 기간이 다른 경우
  - `UNKNOWN`
  - 사용자가 CODEF 참고값을 보고 확인해 입력한 `MANUAL` 값과, 그가 참고한 바로 그 CODEF 값
- 자동 우선순위를 두지 않는다. 충돌한 값은 사용자가 고르기 전까지 `확인 필요`로 두고, 응답에 후보 값과 각각의 출처·기준 기간·갱신 시각을 담는다.
- 사용자의 선택은 그 값(카드·항목·기준 기간) 하나에만 적용하고 다른 달이나 항목으로 넓히지 않는다. 고른 출처, 고른 시각, 당시 후보 값을 기록한다.
- 선택한 뒤 다른 출처의 새 값(예: CODEF 재조회)으로 다시 달라지면, 이전 선택을 그대로 쓰지 않고 다시 충돌로 드러낸다.
- 화면에서는 충돌을 한 곳에 모아 확인하게 하는 것을 권장한다. 세부 형식은 API 명세 단계에서 정한다.

**D-17 취소 귀속·실적 차감·한도 복원**

근거가 되는 사실은 세 가지다. 코드의 취소 귀속 모델은 `RECEIPT_MONTH`(취소전표 접수월 차감, 09271·01664) 하나뿐이다. 09174의 귀속월·한도 복원과 01914의 취소 한도 복원은 미확정이다(D-03). KB 취소 표현은 [취소 표현 구분](domains/codef-kb.md#취소-표현-구분)을 따른다.

1차 모의 취소(BeONE이 만든 모의 승인만 대상)
- 원장에는 항상 기록한다. 원 승인 ID로 연결한 취소 행(취소일, 음수 금액)이다.
- 실적·한도 영향은 그 카드에 확정된 규칙이 있을 때만 반영한다.
- 스냅샷과의 관계(D-16)
  - 원 승인이 최근 수동 스냅샷 입력 시각 뒤에 생긴 모의 승인일 때만 스냅샷 값에서 뺀다.
  - 원 승인이 스냅샷보다 앞서면 스냅샷에 그 승인이 들어 있는지 알 수 없다. 이때는 영향받는 사용액·실적을 `확인 필요`로 두고 임의로 빼지 않는다.
- 혜택 되돌림
  - 취소된 승인에 이미 계산한 혜택(청구할인·적립)과 그 혜택이 쓴 한도는, 되돌리는 규칙이 약관에 확정된 카드만 줄인다.
  - 확정되지 않은 카드는 해당 혜택과 잔여 한도를 `확인 필요`로 둔다.
  - 부분취소로 원 미만이 생기면 D-03 미확정이므로 `확인 필요`로 둔다.
- 부분취소: 여러 번 할 수 있고, 합계가 원 승인 금액을 넘지 않는다. 남은 취소 가능 금액을 응답에 담는다. 모의 취소마다 `Idempotency-Key`를 받는다(D-14 원칙 6).
- 다른 달 취소: 취소일이 원 승인과 다른 달이면 귀속월은 카드의 확정 규칙(`RECEIPT_MONTH` 등)으로만 정한다. 규칙이 없는 카드는 두 달 모두 영향받는 값을 `확인 필요`로 둔다.
- 취소의 취소(재승인)는 받지 않는다.
- 응답: 취소 뒤 다시 계산한 결과에는 확정 규칙으로 바뀐 값과 `확인 필요`가 된 값을 구분해 담는다.

2차 CODEF 취소 행(KB `0301`)
- 전액 취소만 반영한다. 매칭은 승인번호 일치로만 한다.
  - Type1: 취소금액이 이용금액과 같을 때만 승인과 전액 취소로 넣는다. 금액이 다르면 부분취소일 수 있으므로 넣지 않고 원장 불완전으로 둔다.
  - Type2: 같은 카드·같은 승인번호의 정상 행이 정확히 하나이고, 취소 행 금액의 절댓값이 승인 금액과 같을 때만 짝짓는다. 금액이 작으면 부분취소 후보로 보고 넣지 않으며 원장 불완전으로 둔다.
- 취소일: 응답에 취소 접수일이 없으므로 원장에는 취소 행으로 기록하되 귀속월은 `확인 필요`로 둔다. `RECEIPT_MONTH` 카드라도 접수일을 모르면 실적 차감을 확정하지 않는다.
- 짝이 없는 경우(원 승인 행이 조회 기간 밖 등): 조회 기간을 임의로 넓히지 않고 그 취소 행만 불완전 사유로 남긴다.
- 불완전 범위: 원장 불완전은 해당 카드, 해당 취소 행이 걸친 기간에만 표시한다. 다른 카드나 다른 달로 넓히지 않는다. 응답에 행 단위 사유(부분취소 의심, 짝 없음, 짝 여럿, 판단 불가 행)를 담는다.
- 재조회 중복 방지: 같은 CODEF 응답을 다시 가져와도 원장 행이 두 번 생기지 않게 한다. 중복 판단 키(카드, 승인번호, 승인일시, 금액, 행 형태 등)는 명세 단계에서 정한다. 키로 하나를 정할 수 없는 행은 넣지 않고 불완전으로 둔다.
- 음수 금액만으로 취소라고 판단하지 않는다(#45).
- 매칭 키(승인번호를 승인 행과 취소 행이 공유하는지)는 실계정 관측 전까지 `확인 필요`다. 관측한 뒤 이 결정을 다시 검토한다.

음수 전월 실적(취소가 승인보다 많은 달). **약관 근거 없음, 2026-11-01 사용자 결정**
- 적용 범위: 음수 값의 근거가 확정된 경우에만 아래 규칙을 쓴다. 사용자가 직접 입력한 값이거나, 귀속 규칙이 확정된 취소로 계산된 값이어야 한다. 귀속이 확인되지 않은 취소 때문에 생긴 음수는 그 값 자체를 `확인 필요`로 둔다.
- 판정
  - 최저 실적 기준이 0원보다 큰 서비스: 미충족
  - 실적 조건이 없는 서비스(0원 단일 구간): 조건 없음
  - 0원에서 시작하는 다단계 구간: 음수를 어느 구간에 넣을지 근거가 없으므로 `확인 필요`
- 음수 값은 0으로 바꾸지 않고 보존하며, 응답에도 음수로 보여 준다. 다음 달로 이월하지 않는다.
- 수동 입력에서 음수를 받는다. 출처와 입력 시각은 다른 값과 똑같이 기록한다.
- 이 규칙으로 나온 판정 결과에는 "약관 근거 없음, 사용자 결정" 사실을 표시한다.
