## 지금 가능한 기능
- `develop` 반영: 카드 규칙·입출력 모델과 검증, 날짜에 맞는 검증 규칙 선택, 공통 API 응답·오류 처리, 서비스 한 건의 정률·정액 계산·대상 금액 상한·원 미만 발생 확인·최소 금액·결제 방식·업종 판정·전월 실적 구간 선택(#21), 서비스 하나의 후보 판정·최종 채택 여부·실제 기여액을 나눠 담는 결과 타입과 생성 검증(#29), 한도 없는 비선택형 서비스 하나의 주문 한 건 후보 금액(`ServiceCandidate`) 판정기(#31), 선택된 카드 규칙의 서비스들을 후보·확인 필요·지원 범위 밖으로 나눠 모으는 취합기(`CardServiceCandidateCollector`, #33), 아래 결정기(#35).
- 결정기(#35, `develop` 반영): 취합 결과로 카드 한 장·주문 한 건의 서비스별 최종 채택·기여액과 카드 금액(`OrderBenefit`)을 정합니다(`OrderBenefitDecider`). 한도 없는 비선택형 서비스만 판정하며, 확인 필요·지원 범위 밖 서비스, 중복 관계 미확정·중복 허용, 취소 귀속·할인 매출 실적 제외의 영향이 있으면 카드 금액을 `확인 필요`로 두고 구조화된 사유를 남깁니다. 실제 카드 4종은 한도·선택형 서비스가 있어 대부분 `확인 필요`입니다.
- 작업 브랜치(#38): 규칙 카탈로그·카드·판정일을 받아 규칙 선택부터 주문 혜택 결정까지 한 번에 호출합니다(`OrderBenefitResolver`). 판정일은 호출자 입력이며 주문일로 대신하지 않습니다.
- 연결 단계: 규칙 선택 → 서비스 후보 취합 → 카드 한 장의 주문 혜택 결정까지 연결됐고(선택·결정의 단일 진입점은 작업 브랜치), 카드 간 비교(`CardBenefit`·`Recommendation`)·API·화면·앱에는 연결되지 않았습니다.

## 아직 안 되는 기능
- `OrderBenefit`과 `CardBenefit`·`Recommendation`의 연결과 카드 간 비교·추천(후속 필수), 한도 있는 서비스·선택형 서비스의 판정, 한도 차감, 중복 허용 서비스의 합산, 할인 매출 실적 제외 근거 생성과 원장에서 근거를 자동으로 만드는 연결, 신규 유예 기간·간주 실적 판정, 실적 원장 산출, 주문일·결제일에서 판정일을 정하는 규칙, 월간 최적화.
- 수동 카드·상태·주문 API, CODEF 연동, 모의 승인.

## 사용자 확인 사항
1. 음수 전월 실적(취소가 승인보다 많은 달)의 구간 판정. 권장안: 실적 조건이 있는 서비스는 미충족, 실적 조건이 없는 서비스(0원 단일 구간)는 조건 없음으로 본다. 확정 전까지 거부합니다.
2. 정액 혜택이 결제 금액보다 클 때 결제 금액으로 줄일지. 권장안: 청구 할인은 결제 금액을 넘지 않게 줄이되 약관 근거를 함께 확인. 확정 전까지 산식(`BenefitArithmetic`)은 줄이지 않고, 후보 판정기(#31)는 2026-10-29 사용자 확인에 따라 `확인 필요`로 둡니다(D-13).
3. 원 미만 처리 방식(D-03 미확정). 카드별 공식 근거 확인 전까지 원 미만이 생기면 확인 필요로 둡니다.
4. 업무 API 명세(수동 카드·상태·주문·예정 소비)와 사용자 식별 방식(D-09). 저장소에 명세가 없어 API 작업을 시작하지 않았습니다.
5. CODEF 공식 명세 페이지 3개(developer.codef.io의 `/products/card/common/p/account`, `/products/card/common/p/approval`, `/products/card/common/p/result-check`, 제목 미확인)가 있지만, 본문을 JavaScript로 그려 이 세션 도구로는 내용을 읽지 못했습니다(2026-10-31 확인, 도구 접근 한계이며 명세 부재가 아님). 어댑터를 시작하려면 각 API의 갱신일·버전, 요청 URL·파라미터, 응답 필드와 의미, 오류 코드와 인증 만료·연결 실패 구분, 카드사(기관)별 차이를 확인해야 합니다. 권장안: 브라우저 확장 연결로 읽을 수 있게 하거나 각 페이지 본문 사본을 제공해 주시면 그 내용만 근거로 어댑터를 시작합니다.
6. `OrderBenefit`과 `CardBenefit`의 연결 방식, 카드 단위 사유 우선순위, 공유 한도 배분(D-13 미결). 카드 간 비교를 시작하기 전에 정해야 합니다.
7. 판정일 자동 산정(#38). 주문일·결제일과 카드별 거래 기준일(D-03) 중 무엇으로 규칙 버전을 고를지 근거가 없어 호출자 입력으로 두었습니다. 권장안: 주문 결제 시점(모의 승인일)을 판정일로 쓰되, 기준일이 승인일이 아닌 카드는 결과를 `확인 필요`로 둘지 함께 결정.
